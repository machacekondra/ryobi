Architecture Overview

Understand how Ryobi's components work together to deploy and manage your applications.

Components

Ryobi consists of two binaries:

ComponentDescription
ryobiCLI tool — parses YAML, calls the API, displays status
ryobidServer — API gateway, resource provider, async worker

Request Flow

When you run ryobi deploy app.yaml, the following happens:

ryobi CLI ──[HTTP]──▶ ryobid (Chi router)
                        ├── Frontend controllers (sync CRUD)
                        ├── StatusManager → Queue (PostgreSQL)
                        └── AsyncWorker
                              └── Terraform exec (recipe lifecycle)

Synchronous Operations

Environments and Applications are created synchronously. The CLI sends a PUT request, the server validates and persists the resource, and returns immediately.

Asynchronous Operations

Resources (Terraform-managed infrastructure) are deployed asynchronously:

  1. The CLI sends a PUT request for the resource
  2. The server saves the resource and queues an async operation
  3. Returns 202 Accepted with an operation URL
  4. The async worker picks up the operation from the queue
  5. Resolves the recipe from the environment
  6. Generates Terraform configuration (main.tf.json)
  7. Runs terraform init and terraform apply
  8. Extracts outputs and updates the resource status

Data Storage

Ryobi uses PostgreSQL for all storage:

  • Resource store — JSONB documents with ETag-based optimistic concurrency
  • Operation queue — PostgreSQL-backed queue using SKIP LOCKED
  • Terraform state — Native pg backend with per-resource schema isolation

Deployment

Ryobi itself runs as Podman containers (or as a native binary via systemd):

podman-compose -f deploy/podman-compose.yaml up -d

This starts two containers: PostgreSQL and ryobid.

No Kubernetes required

Unlike similar platforms, Ryobi does not depend on Kubernetes. It runs anywhere you can run Podman or a Linux binary. All application infrastructure is provisioned through Terraform.

Key Design Decisions

Terraform-only

All infrastructure is managed through Terraform recipes. No proprietary DSL or runtime. Leverage the entire Terraform provider ecosystem.

YAML definitions

Applications are defined in simple YAML files. Multi-document support lets you define environments and applications in a single file.

Flat REST API

Simple REST endpoints (/api/v1/...) instead of complex ARM-style resource IDs. Easy to understand, easy to integrate.

Single binary server

ryobid combines the API server and async worker. No microservice sprawl. One process, one database.
