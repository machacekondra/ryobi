Architecture Overview

Understand how Ryobi's components work together to deploy and manage your applications.

Components

Ryobi consists of three binaries:

ComponentPortDescription
ryobi—CLI tool — parses YAML, calls the HTTP API, displays status
ryobid9000 (HTTP) + 9001 (gRPC)Server — HTTP API, gRPC event dispatcher
ryobi-env—Environment agent — registers environment, watches for resources, executes Terraform

Request Flow

When you run ryobi deploy app.yaml, the following happens:

ryobi CLI ──[HTTP]──▶ ryobid
                        ├── Chi Router (HTTP API)
                        ├── StatusManager → Queue
                        ├── Worker → ResourceDispatcher
                        └── gRPC Server
                              ↕ watch stream
                        ryobi-env (environment agent)
                          ├── terraform init/apply/destroy
                          └── ReportResult → ryobid

Environment Agent Lifecycle

Environments are live agents, not static configuration:

  1. ryobi-env starts with a config.yaml defining providers, credentials, and recipes
  2. It registers the environment with ryobid via gRPC
  3. It opens a watch stream and waits for resource events
  4. On shutdown (Ctrl+C), it unregisters and removes the environment

Resource Deployment

Resources (Terraform-managed infrastructure) are deployed asynchronously via the environment agent:

  1. The CLI sends a PUT request for the resource
  2. ryobid saves the resource, queues an async operation, returns 202 Accepted
  3. The dispatcher finds the environment agent via gRPC and pushes a ResourceEvent
  4. ryobi-env receives the event, resolves the recipe from its local config
  5. Generates main.tf.json, runs terraform init + terraform apply
  6. Reports the result (success + outputs or failure + error) back via gRPC
  7. ryobid updates the resource and operation status

Data Storage

Ryobi uses PostgreSQL for all storage:

  • Resource store — JSONB documents with ETag-based optimistic concurrency
  • Operation queue — PostgreSQL-backed queue using SKIP LOCKED
  • Terraform state — Native pg backend with per-resource schema isolation

Deployment

Ryobi itself runs as Podman containers (or as a native binary via systemd):

podman-compose -f deploy/podman-compose.yaml up -d

This starts two containers: PostgreSQL and ryobid.

No Kubernetes required

Unlike similar platforms, Ryobi does not depend on Kubernetes. It runs anywhere you can run Podman or a Linux binary. All application infrastructure is provisioned through Terraform.

Key Design Decisions

Terraform-only

All infrastructure is managed through Terraform recipes. No proprietary DSL or runtime. Leverage the entire Terraform provider ecosystem.

YAML definitions

Applications are defined in simple YAML files. Multi-document support lets you define environments and applications in a single file.

Flat REST API

Simple REST endpoints (/api/v1/...) instead of complex ARM-style resource IDs. Easy to understand, easy to integrate.

Environment agents

Each environment runs as a separate ryobi-env agent with its own credentials and recipes. Server stays lightweight — no Terraform needed.
